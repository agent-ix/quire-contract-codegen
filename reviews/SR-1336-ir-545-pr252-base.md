# SR-1336: CG PR 252 spec review (base)

## Summary

Ticket: IR-545. The PR is spec-only. It adds FR-021-AC-24 and its mutation row, extends two
FR-021 Behavior bullets (the duplicate-request bullet defines a function binding; the claim-order
bullet adds a function-name tie-break), adds TC-031 step 12 and an Expected Results clause, and
adds matrix rows.

The bug is real. I checked it in the code at the base and with my own probe, a throwaway test run
in a detached worktree at the PR head (src identical to the base). `ItemKey`
(`src/oracle/function/mod.rs:1398-1426`) is (call node id, declaring node id looked up by name,
`None` for an unknown name, argument node ids, `refused_name` set only for duplicate-node names).
Two unknown names on one node with equal arguments therefore share one key. `counts > 1` gives
`DuplicateRequest` (lines 1128-1136), and `by_key` keeps only the first item (line 1113). Probe
results, over `function_add("add_fn")` on call node `ITEM_CALL_ADD`:

- (a) `zz_unknown` once: 1 entry, `UnknownFunction { name: "zz_unknown" }`.
- (b) `zz_unknown` and `aa_unknown`, in either order: 1 entry, `DuplicateRequest`. The second
  name is lost.
- (c) `zz_unknown` twice: 1 entry, `DuplicateRequest`.
- (d) `add_fn` and `zz_unknown`, in either order: 2 entries, `UnknownFunction` first (`None` <
  `Some`), then `Generated(add_fn, oracle_call_add_fn)`. That generated entry is the same one
  `add_fn` gets when requested alone.

The expected behaviour agrees with the existing spec:

- FR-021-AC-1 says nothing about whether a duplicate gets one claim or one per copy. The
  `DuplicateRequest` doc comment and `tc_031_ac1_duplicate_request_refuses_every_copy`
  (`items.len() == 1`) fix it at one entry per key. AC-24's "`zz_unknown` twice still yields one
  entry" keeps that.
- Under the new binding definition (name plus argument operands), an item that names a different
  unknown function is not a copy. That definition matches the code for every declared case. A
  name declared once maps 1:1 to a node id. An ambiguous name maps to the highest-sorted node id.
  A duplicate-node name keys on `refused_name`. Two items with the same name always share a key.
- A byte-order tie-break is what Rust `String`/`Option<String>` `Ord` gives. It is
  permutation-independent (AC-13). It is also the order the code already uses to break the
  FR-021-AC-22 same-node tie (`refused_name`).
- No new refusal variant is needed. `ExactFunctionRefusal::UnknownFunction { name }` already
  exists and is re-exported from `src/lib.rs:73`. interface-001
  (`spec/core/functional/interface-001-codegen-api.md:142-143`) names only the input and output
  types, not the refusal variants, so it needs no change.

AC-24's examples check out. 'aa_unknown' sorts before 'zz_unknown', and an unknown name sorts
before a declared one (`None` < `Some`). "Equal to the entry that item gets when requested alone"
holds for both items of the mixed case. The first mutation (the code at the base) is real, and the
third (a hash or request-position tie-break) is plausible. The second is not a mutant: FND-001.

## Verdict

The criterion's expected behaviour is right and agrees with FR-021-AC-1, AC-13 and AC-22. One
medium finding: the mutation row names an alternative implementation that is in fact correct.
Four low findings cover wording and testability. Mergeable once FND-001 is fixed. The low findings
are cheap to fix in the same round.
