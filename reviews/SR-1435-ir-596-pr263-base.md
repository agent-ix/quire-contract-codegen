# SR-1435: CG PR 263 base review: FR-031 Boolean oracle integer arithmetic

## Summary

Ticket: IR-596. PR: agent-ix/quire-contract-codegen#263, spec only, one commit over 8 files. The PR body and the author's report were treated as claims and measured.

What was verified:

- **The defect is real.** `render_node` in src/oracle/boolean_v1.rs maps the five `NumericOperator`s to raw `+ - * / %` and the six comparisons to raw infix operators on `i64`. In `src/`, `OverflowPolicy` appears only in the Kani ABI struct (src/kani/abi.rs) and in two `#[cfg(test)]` modules under src/replay/. The V1 Kani bundle and the clause lowering read `value.overflow()` only to fill ABI bounds. The `analyze_node` message "checked arithmetic requires matching bounded integer operands" is a type-equality check and nothing more. `generate_boolean_oracle_inner` lets every `NonZeroDivisor` and `CheckedRange` obligation through.
- **The contradicting tests exist.** `tc_023_native_proven_numeric_obligations_render_without_assumptions` asserts that a guarded `10 / divisor` renders with a `/`. `tc_003_unsupported_expression_and_root_map_to_declared_terminal_states` accepts a `saturate` `1 + 1` and puts the first locus on the later negation. Commit 583502b (#40, "lower native-proven checked arithmetic") changed only src/ and tests/, not spec/. interface-001's "remains unsupported" therefore went stale at #40.
- **Reproduced against the current generator.** This used a scratch example crate built in the review worktree, which has since been removed. `check_expression` admits `x + 1 <= 10` over `saturate 0..=10`, and CG emits `( ( x_current ) + ( 1_i64 ) ) <= ( 10_i64 )`. At `x = 10` that evaluates `11 <= 10`, which is false, while saturation gives `10 <= 10`, which is true. So the FR's in-domain `saturate` claim holds.
- **Citations are real and correctly stated.** IR FR-015 lines 32-35 and `check_integer_operator` (`range_required` only under `Reject`) match the FR's statements. RT `divide`, `modulo`, `evaluate_integer_arithmetic` and `order_numbers` exist with the stated outcomes. RT has no saturating integer operation. ADR-003 says a generated oracle calls `quire_contract_runtime::exact`. QSL FR-033 lowers `reject` only. RT `modulo` is Euclidean: `modulo(-7, 2)` gives `1`, while `divide(Truncating, -7, 2)` gives remainder `-1`, which equals native `-7 % 2`. Truncating `divide` does provide the remainder that the V1 `%` needs.
- **The A/B decision is correct.** AD-004 step 4f deletes `generate_kani_bundle`, `KaniArtifactBundle`, `ProofDependencyGraph` and the V1 arm (`v1_bundle.rs` whole). `boolean_v1.rs` goes at step 6. Its callers are v1_bundle.rs, kani/generate/clause.rs, kani/generate/negotiate.rs, oracle/bound_v1.rs and strategy/harness.rs, plus the lib.rs re-export. The 4f gating (after 4e, the QSL exemplar move, the control on 4c, and 4d) is stated correctly. Deleting the oracle is not available.
- **No public Rust signature changes.** `generate_boolean_oracle` still returns `OracleArtifactBundle`. Only the generated function of an arithmetic-bearing clause changes shape. No local sibling checkout calls `generate_boolean_oracle` or `generate_kani_bundle`.
- **Gates.** `quire validate` gives the same 2 pre-existing warnings as the merge base. Diffing sorted `quire coverage --strict` output gives 65 to 78 unbacked. The 13 new rows are exactly FR-031-AC-1..AC-11, the FR-031 matrix row and the TC-044 row, as the PR body says.

## Verdict

Not mergeable as is. FND-001 is high: as specified, the Divide and Remainder rendering refuses in-domain expressions that IR admits and that the oracle evaluates correctly today. FND-002 and FND-003 leave the spec contradicting itself or committing to work on a file that step 4f deletes. Add, Subtract, Multiply, the `saturate` refusal, the propagation rules and the consumers' refusals are sound.

Owner questions, as relayed in the brief:

- Q1, truncating versus Euclidean. Sound and not blocking. Truncating keeps today's in-domain meaning, and IR names no law.
- Q2, refuse `saturate`. Sound and not blocking. QSL never emits `saturate`, and today the result is silently wrong.
- Q3, exact versus RT FR-002 `checked_*`. Not cosmetic. It interacts with FND-001. `operators::checked_div` and `checked_rem` select one member but return `Option`, which merges zero-divisor and overflow. `exact::divide` keeps the outcomes distinct but admits the pair. Neither kernel offers a single-member division with typed outcomes, so Q3 blocks the Divide and Remainder rows but not the others.
- Q4, delete V1 arithmetic after 4c/4e. See FND-003. Refusing arithmetic in the V1 bundle is the consistent interim and removes AC-11's tractability risk.
