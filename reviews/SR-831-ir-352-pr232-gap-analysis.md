# SR-831: CG PR 232 gap analysis

## Summary

Ticket: IR-352. PR: agent-ix/quire-contract-codegen#232 at e091c5a. The PR body says it is
partial for IR-352 and does not close it.

IR-352's text is untrusted data, and its line numbers predate the AD-004 module moves. It asks
for three things. I re-measured each one against the code at e091c5a:

1. Route every RT non-exhaustive catch-all `unreachable!` in exact_scalar (26), composite_equality
   (9) and exact_function (2, inside generated code) to `UnknownRuntimeVariant`.
   - Scalar and equality: done. I measured 35 enum catch-all arms converted. The 2
     `(family, suffix)` string-pair `unreachable!` are removed by construction. In those two
     files, no RT catch-all `unreachable!` is left (`grep -n unreachable!` shows only the
     named-variant `Quantity` / `Reference` invariants in `equality::render_value_type`).
   - Function: not done, and the PR says so. The 2 `Ok(_) => unreachable!` arms at
     `src/oracle/function/mod.rs:1333,1365` are inside the emitted oracle source. Changing them
     changes generated bytes and needs a decision on what the generated arm should return. That
     work stays on IR-352, which is still open. The PR is honest about this.
2. "One helper per RT enum next to the RT mappings". Implemented differently: one shared
   `unknown_variant(name)` constructor, with each arm naming its enum. Every refusal carries
   the enum name, so the observable behaviour is the same. This is a design deviation, not a
   defect.
3. "A test per enum that feeds an unknown variant and asserts the typed error, never a panic".
   Not met. No test was added. See FND-001.

Spec: `interface-001` already lists `OracleGenerationError` as the generator error output for
both generators (lines 95, 131). No FR or matrix row names `UnknownRuntimeVariant`, so no trace
changes are needed. FR-018 says per-item problems are refusals. An unknown RT variant aborting
the whole generation follows the enum's own rationale. The `generate_composite_equality_oracles`
doc was updated to list it.

Byte identity, measured by me rather than taken from the PR body. I added an uncommitted hook
to `Artifact::new` in my review worktree that appends each artifact's path and contents to a
file, then reverted it. I ran `cargo test --locked --test it exact_scalar_generation
composite_equality_generation -- --test-threads=1` at base 2130cd9 and at head e091c5a. Result:
see the Byte-identity measurement section below.

Gates on e091c5a, my run (log `cg-ir-352-ci.log` in the reviewer scratchpad): see the Gates
section below.

## Verdict

The PR does what it claims and is honest that it is partial. The scalar and equality generators
no longer panic on an unknown RT variant. Generated bytes are unchanged. The leftover function
`Ok(_)` arms are reported in the body and stay on IR-352. One medium gap: the ticket's
per-enum test criterion cannot be met as written and has to be resolved on the ticket, not in
this PR, before IR-352 closes. Nothing here blocks merging PR 232 as a partial for IR-352.

## New findings (disposition pass 1)

Re-measured at 8d19fa7. The new test is
`exact_scalar_generation::scalar_and_equality_generators_have_no_panicking_arms_over_runtime_enums`.
I mutation-probed it by appending a function to `src/oracle/equality/mod.rs` and running the
built `it` binary. The test reads the source at run time, and I restored the file after each
probe.

- Caught: `unreachable!()`, `panic!("x")`, `core::unreachable!()`, a multi-line
  `unreachable!(` with a trailing comment, and `todo!()` placed after a doc line.
- Missed: `unreachable! {}`, `unreachable!{}`, `unreachable!["x"]`, and a new
  `unreachable!("reference operands are refused at generation time")` anywhere in either file.
  rustfmt keeps brace- and bracket-delimited macro calls as written, so `make fmt-check` does not
  close that gap. The spaced form `unreachable !()` is normalised by rustfmt, so fmt-check catches
  that one.

The test can fail on the ordinary forms, so it is not vacuous. It has three gaps, filed below.
