## Summary

Ticket: IR-1515. PR #791 (spec only, one commit 995a89f7 on origin/main a52a000e) adds FR-015-AC-133, AC-134 and AC-135, three FR-015 requirement bullets, TC-025 steps 52 and 53 with mutants M1..M8, the AC-48 row tail, the TC-025 step-14 tail and the tests.md AC-48 row. Method: spec-review/base. Reviewed read-only in /home/peter/dev/worktrees/IR-1515-review against the merged CG #788 code (src/kani/identity.rs, src/kani/generate/collection.rs, src/kani/generate/collection/operation.rs, src/kani/generate/negotiate.rs, src/kani/generate/outcome.rs), AD-003 E-1, qsl-replay at 68acd90, and the SR-788001..003 rulings on IR-1507.

## Verdict

**CHANGES REQUIRED.** AC-133 (cardinality plus element domain) and AC-134 (every drawn field is a read) follow the SR-788003 FND-002 ruling and match the drawn-state semantics the harness identity already uses; the occurrence wording of gap 1 is already in AC-48 from #788, so nothing more is needed there. AC-135 picks the binding-check branch of the SR-788003 FND-003 ruling, which is right, but binds the claim to the wrong thing: a key the caller supplies rather than the clause node's key that CG can resolve itself, on a reading of AD-003 E-1 that the decision text does not support. The other findings are about what the binding compares and about request and record shapes the ACs imply but do not state.

| FND-001 | high | AC-135 binds the claim's NodeKey to a key the caller supplies, not to the selected clause node, so it does not close the SR-788003 FND-003 misattribution. The request already carries the claim (`ObligationItem::V2Clause { package, clause, claim, .. }`, outcome.rs:82-92). A caller that sends another obligation's identity can send the matching wrong key too: the check compares two caller inputs with each other, and step 53 makes this explicit ('the keys written by hand in the test, not derived from the node ids'). No case or mutant can fail when the supplied key is not the clause node's key. The stated reason, 'CG derives no NodeKey from a CheckedNodeId (AD-003 E-1)', is not what E-1 says. E-1 says CG never computes a preimage, hashes an identity, or 'derives a node from a replay transcript' (AD-003:168-179). CG already resolves this exact key from the admitted package. `StateClauseReplay` compares `package.structural_key(clause_node).and_then(checked_node_key)` with QSL's `call_site` node (src/replay/state_clause.rs:617-623, `ClauseSelectionMismatch`). `CheckedGraph` keys every node through QSL's own `qsl_replay::WireGraph` (src/oracle/checked_graph.rs:114-127). QSL's `replay_state_clause` then refuses an envelope whose clause node is not the recompiled one (qsl-replay execute/state_clause.rs `ClauseIdentityMismatch::Node`). Fix: compare the claim's NodeKey with the selected clause's key that CG resolves from the admitted package, through the same resolver replay uses. Drop the request-supplied key and the E-1 sentence, and change step 53 so the expected key comes from the package (or from QSL's call_site), not from the request. | spec/kani/functional/FR-015-bounded-kani-obligations.md:947 |
| FND-002 | medium | AC-135 makes 'a differing model or producer-assigned ordinal alone is admitted' a requirement, and step 53(c) and mutant M7 lock it in, with no reason given. AC-48 and AD-003 E-1 say distinct obligations at the same node/model have distinct ordinals. A claim carrying the identity of another obligation at the same clause node (different model or ordinal) with a correct record is still carried onto this harness, the same misattribution AC-135 gives as its motivation. | FND-003 | medium | AC-135 says 'the request supplies QSL's issued key with each selected clause node' in the present tense. `ObligationItem::V2Clause` has no such member today: it carries `package`, `clause`, `claim` and `dependencies` (src/kani/generate/outcome.rs:82-92). The AC therefore needs a new public request field, a driver change to fill it, and an update to the public codegen API spec (spec/core/functional/interface-001-codegen-api.md). None of these is named as a prerequisite. IR-1518 likewise says 'The request carries the QSL-issued NodeKey'. Separately, every existing V2 clause fixture carries an arbitrary key that is not the clause node's key: `claim_of` uses NodeKey('producer-issued', ['obligation'], 0) (tests/it/v2_clause_obligation_identity.rs:76-84), and `fixture_obligation` in src/kani/test_support.rs:316-324 does the same. All of them will be refused once AC-135 lands, and IR-1518's scope does not mention this. If FND-001's fix is taken, the request field goes away, but the fixture fallout stays and should be named in IR-1518. | spec/kani/functional/FR-015-bounded-kani-obligations.md:947 |
| FND-004 | medium | AC-133 says a claim's record 'gives a sequence-valued field ... a cardinality range or an element domain, at any nesting level'. The public record member `V2ClauseRead` holds a flat `minimum`/`maximum` i64 pair (src/kani/identity.rs:388-399). It cannot carry an element domain, so a claim cannot express what AC-133 compares. The AC does not say how the read domain is represented: a recursive domain type, or reuse of `SymbolicBounds`. Nor does it say what the refusal's `selected` diagnostic then holds. Two implementers would build incompatible public records. State the record shape, either in AC-133 or in a sibling interface criterion, and name it in IR-1517. | spec/kani/functional/FR-015-bounded-kani-obligations.md:945 |
