# SR-870: CG PR 237 spec review, base and correctness

## Summary

Ticket: IR-352. PR: agent-ix/quire-contract-codegen#237 at 6d0e02a4770c6b77bc4b08ea46a3978015c6c1bc.
The merge base is origin/main (81a9c69fb1e55066204a2e8cbe94232169cacdcd), so the branch is current
and merges cleanly. The PR is spec-only: FR-021 gains two Behavior bullets, AC-19 to AC-21 and three
mutation rows; TC-031 gains step 8 (old step 8 is now 9); tests.md gains one Planned row.

What I verified against the code and the runtime, not the PR body:

- Negate. `classify_body_shape` (src/oracle/function/mod.rs:657-670) refuses any `Scalar` body whose
  operator is not `Add`, `Subtract` or `Multiply` with `ExactFunctionRefusal::UnsupportedOperator`.
  `render_body` (:1313) is reached only through `finish` over the classified survivors, so the
  `IntegerOperator::Negate => unreachable!` arm at :1320 is a generation-time arm, never emitted,
  and redundant behind the earlier refusal. The author's reading is right. The test
  `tc_031_unsupported_operator_refuses_unary_negate_scalar_body` already asserts the refusal.
- Outcome arms. The two `Ok(_) => unreachable!(...)` arms at :1333 and :1365 are inside the emitted
  scalar and equality body templates. Every emitted scalar and equality body contains one, so the
  claim "generated bytes change for every scalar and equality function body" is correct.
- Runtime. At the locked RT revision ccc722bd56c64b264070a30a14020efd0bf4a0f4, `Outcome<T>` is
  `#[non_exhaustive]` with exactly `Completed`, `Undefined`, `Refused`, `Incomplete`; `Refusal` is
  `#[non_exhaustive]` and `CheckedInvariant` is documented "a checked-program invariant failed during
  evaluation; unreachable for an admitted program". RT origin/main e88c0680ef8ae4c24a28db836a6654c171b5598f
  has the same four variants. Because the generated crate is a separate crate, a wildcard arm over
  `Outcome` is required to compile; the generated match cannot be exhaustive.
- Choice of refusal. RT has no unknown-variant or unsupported refusal (its own module doc says
  `unsupported` is a provider disposition, not an evaluator outcome). `Incomplete` needs an
  `Incomplete` record naming a charge point and `Undefined` claims no mathematical value; both would
  be false. `CheckedInvariant` is the only existing variant whose meaning fits (the generated
  program's own assumption about the runtime failed), and FR-021's Description already routes an
  unreachable `check` failure there. It is overloaded (FR-021-AC-7's depth bound also returns it)
  and loses which variant arrived, but a dedicated refusal would be an RT change and is not needed
  for prerelease. I accept the choice.
- FR-014-AC-9 is about FR-014's own scalar oracles; FR-018-AC-8 is about FR-018's equality oracles
  and already uses `CheckedInvariant` for an environment failure. Neither overlaps or contradicts
  the new ACs.
- Goldens. There are no stored byte goldens for function oracles. tests/it/exact_function_generation.rs
  asserts substrings (`lib.contains(..)`) and determinism compares runs. The code PR therefore has no
  golden files to update; the PR body's "and goldens" is inaccurate but harmless (data, not spec).
- Gates. `make TRUSTED_HOME=<scratch home> spec` exits 0 with the same 8 module-loader diagnostics
  as main. `quire coverage --strict --json`: main 66 unbacked rows, 211 backed of 320; head 66
  unbacked, 211 backed of 323 (the three Planned criteria are added, no backed count changes,
  status lies 0 on both).
- Hygiene. Title has no bare ticket id; body opens "Part of IR-352"; no short SHAs in the diff or
  body.

## Verdict

The design is right and the three arms are correctly diagnosed. One high finding: the amended text
does not deliver the stated goal "generated code never panics", because the emitted
`checked_package()` keeps an `.expect(..)` that no new AC catches. One low finding is pre-existing
staleness in AD-004 on the same subject. Not mergeable until FND-001 is fixed.
